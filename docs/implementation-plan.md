# 둘길 구현 계획
작성일: 2026-10-13 (Asia/Seoul)

## 1. 문서 기준과 결정 상태
이 문서는 PRD, 기능명세서, 최신 첨부 유저플로우를 바탕으로 만든 구현 제안이다. 원본 요구사항을 수정하거나 기술 선택을 확정하는 문서가 아니다.
- prd.md: 업로드된 PRD_2026-10-13(1).md 내용 그대로.
- feature-spec.md: 업로드된 기능명세서_2026-10-13(1).md 내용 그대로.
- user-flow.md: 최신 couple-date-user-flow(2).md 내용 그대로. 이전 첨부와 동일한 경우 중복 보관하지 않는다.
- 코드, 패키지 설치, 외부 API 연결, 배포는 아직 수행하지 않았다.

## 2. 제품 구조와 MVP
첫 버전은 모바일 우선 반응형 웹으로 제안한다. 핵심 경험은 '두 사람의 조건 → 실행 가능한 코스 → 함께 확정 → 완료 후 기록'이다.

| 단계 | 구현 내용 | 완료 판단 |
|---|---|---|
| 기반 | 로그인, 커플 공간, 초대, 접근 제어 | 서로 다른 두 계정 연결, 제3자 접근 차단 |
| 계획 | 개별 취향, 날짜·지역·시간·예산·이동 수단 입력 | 저장한 조건 재사용, 시간·예산 유효성 검증 |
| 추천·편집 | 제한된 지역의 검증된 장소 데이터로 코스 생성, 이유·예상값 표시, 장소 교체·순서 변경 | 조건을 만족하는 코스 저장 및 수정 후 재계산 |
| 실행·기록 | 예정 코스 목록, 완료 처리, 사진·메모·후기, 개인/커플 범위, 타임라인 | 실제 데이트 날짜로 기록, 권한별 조회 |
| 생활 관리 | 기념일 CRUD, 연결 해제·삭제 정책, 신고 접수·검토 | 접근 회수와 데이터 처리 결과 확인 |

소셜 로그인 확대, 고도화된 AI 추천, 자동 위치 추적, 실시간 공동 편집, 푸시 알림은 후속 단계로 제안한다. 기념일 알림 설정은 저장할 수 있어도 실제 발송 채널과 작업 스케줄러를 구현하기 전에는 '발송 제공'으로 표시하지 않는다. 관리자 기능은 신고 검토 범위부터 시작하고 개인 기록 전체 열람 권한을 기본 제공하지 않는다.

## 3. 권장 코드 구성 (제안)
TypeScript 기반 단일 웹 저장소로 시작한다. Next.js(App Router)로 화면과 서버 API를 구성하고, PostgreSQL로 관계 데이터를 저장한다. Supabase Auth/Storage/PostgreSQL을 사용하는 방안을 제안하되 실제 도입·비용·버전은 개발 시작 시 공식 문서와 요구 조건을 확인한다. 지도·장소·경로 제공자는 아직 미정이다.

| 영역 | 책임 |
|---|---|
| app | 페이지, 레이아웃, API 진입점 |
| features/auth, couple | 인증, 초대, 연결과 해제 |
| features/preferences | 개별 취향과 데이트 조건 |
| features/courses | 추천 결과, 편집 UI, 확정 |
| features/memories | 업로드, 기록, 타임라인 |
| features/anniversaries | 기념일과 일정 |
| server/services | 권한 확인, 상태 전이, 트랜잭션 |
| server/recommendation | 장소 필터, 점수, 코스 조합, 제한 검증 |
| server/providers | places/maps/routing 공급자 인터페이스와 mock 구현 |
| lib | 공통 검증, 날짜·금액·오류 처리 |
| db/migrations | 스키마, 제약, 접근 정책 |
| tests | 권한·상태·추천 제약 테스트 및 핵심 E2E |

외부 제공자 응답을 화면에서 직접 사용하지 않고 공통 Place/Route 모델로 변환한다. 브라우저 공개용 지도 키는 공급자 정책에 맞춰 제한하며 서버 비밀 키는 저장소에 넣지 않는다. 데모 데이터와 실제 장소 데이터는 명시적으로 구분한다.

한 사용자는 활성 커플 공간 한 개에만 속하고, 공간은 활성 멤버 최대 두 명으로 제한한다. 동시 초대 수락은 트랜잭션에서 잠금과 재검증으로 처리한다. 코스 방문 순서는 코스 내에서 유일하게 유지한다. 금액은 원 단위 정수, 시간은 UTC 저장/사용자 시간대 표시를 기본으로 하며 날짜만 있는 기념일은 DATE로 구분한다.

## 6. 서버 작업/API 초안
| 작업 | API 제안 | 핵심 검사 |
|---|---|---|
| 공간 생성·초대 | POST /api/couples, POST /api/couples/invites | 인증, 멤버 수, 기존 연결 |
| 초대 수락 | POST /api/couples/invites/accept | 토큰 해시·만료·일회성, 동시 수락 |
| 취향 저장 | PUT /api/preferences/me | 본인만 수정 |
| 추천 | POST /api/recommendations | 조건 검증, 제한된 후보, 결과 없음 안내 |
| 코스 생성·수정 | POST /api/courses, PATCH /api/courses/:id | 소유/멤버 권한, revision 충돌, 재계산 |
| 공동 확정 | POST /api/courses/:id/confirm | 현재 revision에 대한 두 명 동의 |
| 완료 처리 | POST /api/courses/:id/complete | 상태, 실제 완료 날짜 |
| 기록 | GET/POST /api/memories, PATCH/DELETE /api/memories/:id | visibility, 작성자 편집 권한 |
| 사진 | POST /api/uploads/sign, POST /api/uploads/complete | 형식·용량·소유자, 실제 업로드 검증 |
| 기념일 | GET/POST /api/anniversaries, PATCH/DELETE /api/anniversaries/:id | 활성 멤버 권한 |
| 연결 해제 | POST /api/couples/disconnect | 처리 정책 확인, 즉시 접근 회수 |
| 계정 삭제 | DELETE /api/account | 재인증, 공유 자료·사진 삭제 정책 |
| 신고 | POST /api/reports, PATCH /api/admin/reports/:id | 인증/관리자 역할, 조치 기록 |

목록 API는 페이지네이션·검색 범위를 정의한다. 오류는 코드와 한국어 안내를 함께 반환한다. 외부 호출에는 시간 제한을 두며, 재시도 가능한 오류와 조건 불충족을 구분한다.

## 7. 추천 로직 초안
1. 지역·날짜·시간·예산·이동 수단 입력을 검증한다. 지역만 입력한 경우 부족한 조건을 보완하거나 적용 기본값을 보여준다.
2. 검증된 장소 후보를 가져오고, 알려진 휴무·폐업·회피 조건을 제외한다. 영업 정보를 확인할 수 없으면 이용 가능 여부 미확인으로 표시한다.
3. 공통 취향에 가점을 주고 양쪽의 개별 취향도 반영한다. 한쪽의 명시적 회피 조건을 공통 점수로 덮지 않는다.
4. 식사·카페·활동 등을 조합하고 실제 이동 수단의 예상 이동 시간과 체류 시간을 합산한다.
5. 이용 가능 시간과 예산을 넘는 후보는 제외한다. 비용이 미확인인 장소는 완전히 검증된 예산 적합 코스로 표시하지 않는다.
6. 상위 후보에 선택 이유, 예상 비용/시간의 출처와 확인 시각을 붙인다.
7. 만족하는 결과가 없으면 예산·시간·지역 조정안을 제시한다.

초기에는 규칙 기반으로 검증 가능한 결과를 만든다. LLM을 추가하더라도 장소 존재 여부·영업·비용·경로를 생성 텍스트에 맡기지 않는다. 지도에 장소를 표시하는 기능과 실제 교통 경로 계산은 별도 능력으로 취급한다. 직선 연결을 실제 도보/대중교통 경로라고 표시하지 않는다.

## 8. 원본 플로우 보완 제안
- 저장 후에는 예정 코스 상세로 이동한다. 데이트 완료 후 기록 작성으로 진입하며, 과거 데이트 직접 기록도 허용하는 방안을 제안한다.
- 초대 링크로 진입한 비로그인 사용자는 로그인 후 원래 초대로 돌아온다. 만료·이미 사용·연결 중 상태를 안내한다.
- 연결 전에는 개인 홈과 개인 기록만 접근하도록 하고 커플 전용 화면은 제한한다.
- 코스 상태는 draft → planned → completed 또는 cancelled로 구분한다. 두 사람이 현재 revision을 확인하면 planned로 전환한다. 확정 후 장소·시간 변경 시 기존 확인을 무효화한다.
- 기록은 코스와 별도 엔티티다. 공개 범위는 public 없이 private/couple로 시작한다. 작성자만 편집하고 공동 편집은 추후 정책으로 다룬다.
- 공동 코스 변경은 revision으로 충돌을 감지하며 덮어쓰기 전에 재조회한다.

## 9. 권한·삭제 정책 초안과 미결정 사항
개인 기록은 작성자만, 커플 기록은 작성자 및 해당 공간의 활성 상대방만 조회한다. 서버와 DB 정책 모두에서 검사하고 사진도 비공개 저장소와 짧은 유효기간의 URL을 사용한다.
연결 해제 즉시 상대 접근·초대·새로운 공동 편집을 중단한다. 제안은 작성자가 자신의 기록을 유지하고 상대 작성 기록에는 접근하지 못하도록 하는 것이다. 공동 코스 복사, 상대가 업로드한 사진, 재연결 시 과거 기록 복구 범위는 구현 전 명시적으로 결정한다. 결정 전에는 파괴적인 자동 삭제를 구현하지 않는다.
계정 삭제는 재인증 후 대상 목록을 보여주며 DB와 파일 저장소의 처리 상태를 추적한다. 개인 기록을 삭제하되 공동 자료 유지/익명화 여부는 별도 확정해야 한다. 신고 검토는 신고 대상과 필요한 범위에만 제한한다.

추가 결정: 지도·장소·교통 공급자, 실제 경로 자동 수집 여부, 비용 산정 단위(두 명 총액), 영업 정보 신뢰도, 알림 채널, 소셜 로그인 제공자, 공동 확정의 개인 사용 대안. 본 계획은 비용을 두 명 총액으로 제안하며 원본 명세에 확정된 내용은 아니다.

## 10. 구현 순서와 검증
1. 프로젝트 초기화, 환경변수 예시, 공통 모델·검증·DB 마이그레이션.
2. 인증과 커플 연결, 권한 정책부터 구현. 두 계정/제3자/동시 수락/만료 초대 검증.
3. 데모 장소 데이터로 조건 입력 → 추천 → 편집 → 저장 흐름. 시간·예산 초과 및 결과 없음 검증.
4. 실제 제공자 어댑터 연결. 영업 정보 누락, 외부 API 실패, 경로 미제공 안내 검증.
5. 완료·기록·사진·타임라인. 개인 사진 URL 접근 차단, 업로드 실패 및 고아 파일 정리 검증.
6. 기념일·신고·연결 해제·계정 삭제 정책 구현.
7. 가입 → 두 계정 연결 → 공동 확정 → 완료 → 기록 조회 E2E 및 모바일 화면 확인.

시작할 코드는 기능 전체를 동시에 펼치기보다 1~3단계의 한 흐름을 완성하는 것을 우선한다. 원본 기능명세 수용 기준과 구현·검증 결과를 이후 별도 추적한다.
